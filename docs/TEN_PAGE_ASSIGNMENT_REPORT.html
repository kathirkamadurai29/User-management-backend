1.1 Problem Statement & Architectural Motivation

In multi-tenant Software-as-a-Service (SaaS) systems, organizations share underlying computing infrastructure while demanding absolute privacy, operational independence, and reliable security. Traditional web applications often suffer from two major architectural anti-patterns:

  • Leaky Query Abstractions: Many systems rely on soft tenant filters passed in client request bodies or query parameters. Without strict cryptographic binding, malicious tenants can forge parameters and enumerate other organizations' user directories.
  • Credential Overloading: Issuing developer API keys at initial signup conflates interactive user browser sessions with machine-to-machine integrations, drastically widening the attack surface and complicating token revocation.

TenantCore was engineered to solve these exact challenges. We designed a layered architecture where tenant identities are sealed within cryptographically signed JSON Web Tokens (JWTs), database queries are forcibly scoped at the database adapter layer, and authentication is separated into two distinct tracks: browser session tokens and developer API keys.

2.3 Security Perimeters & Network Boundaries

The architecture enforces defense-in-depth across all boundaries:

  • Transport Layer Security (TLS 1.3): All external and inter-service communication is encrypted in transit. Free SSL certificates are auto-renewed by Vercel and Render.
  • CORS Policy Lockdown: The backend strictly restricts permitted origins to authorized production frontend domains and local developer environments, rejecting unauthorized cross-origin requests.
  • Zero Trust Tenant Scope Resolver: Client identifiers are never extracted from user-controlled parameters. The authenticated tenant context is derived solely from verified cryptographic signatures.

3. Multi-Tenant Architecture & Logical Isolation Section 3

3.1 Multi-Tenancy Strategy Evaluation

Designing multi-tenant cloud applications involves evaluating three primary isolation models against cost, operational overhead, and security:

Architecture Model Resource Isolation Operational Complexity Cost at Scale Evaluation for TenantCore
Database-per-Tenant Physical (Highest) Very High (N database instances/migrations) Very Expensive Overkill for initial tier; high idle overhead.
Schema-per-Tenant Logical (Namespaces) Moderate (Dynamic schema DDL scripts) Moderate Complex migrations; poor NoSQL compatibility.
Shared DB / Partitioned Logical (Query Scoped) Low (Single schema, indexed partitions) Optimal (Cost Efficient) Selected Model: Scalable, performant, enterprise-tested.

3.2 Hard Query-Level Partitioning Implementation

TenantCore utilizes a shared MongoDB database with Hard Query Partitioning. Every tenant user document is permanently indexed with a mandatory client_id field. The backend implements a non-bypassable scoping pattern in Python: 

# Authentication Middleware extracts verified tenant from JWT:
tenant = request.state.tenant  # Contains {"client_id": "cli_9e7196a4bb2f4e89"}

# Users Repository enforces query injection on EVERY database access:
@router.get("/users/{user_id}")
async def get_user(user_id: str, request: Request):
    # Query forcibly matches BOTH the document _id AND the caller's client_id:
    user = await db.users.find_one({
        "_id": ObjectId(user_id),
        "client_id": request.state.tenant["client_id"],
        "is_deleted": False
    })
    if not user:
        # Crucial security decision: Return 404, never 403
        raise HTTPException(status_code=404, detail="User not found")
    return serialize_mongo_doc(user)

3.3 The "HTTP 404 vs 403" Security Decision

Zero-Knowledge Security Obscurity Principle:
When Tenant B attempts to read, mutate, or delete a resource owned by Tenant A, the system returns HTTP 404 Not Found rather than HTTP 403 Forbidden. Returning 403 acknowledges that the resource exists, enabling malicious attackers to enumerate valid user UUIDs across other corporate tenants. Returning 404 ensures zero knowledge leakage.

4.2 JWT Claims Specification & Privilege Scopes

The platform issues cryptographically signed HS256 tokens with typed payload schemas:

Token Type Audience / Caller Payload Claims Structure Permitted Operations
Session JWT Browser Dashboard (/) { "sub": client_id, "role": "client", "type": "session", "exp": ... } Tenant user CRUD, avatar upload, activity logs, generating API credentials.
API JWT External Systems (cURL/SDK) { "sub": client_id, "role": "client", "type": "api", "exp": ... } Programmatic tenant user CRUD. Restricted from regenerating credentials.
Super Admin JWT Super Admin Portal (/admin) { "sub": admin_id, "role": "super_admin", "type": "session", "exp": ... } Cross-tenant directory, pause/resume tenants, user drilldown, platform metrics.

5. Dual Database Architecture: Supabase vs. MongoDB Section 5

5.1 Polyglot Persistence Engineering Rationale

The technical specification mandated the practical demonstration of both Supabase (PostgreSQL) and MongoDB. Rather than introducing artificial redundancy, TenantCore implements polyglot persistence where each database engine is assigned the workload that matches its core architectural strengths:

Evaluation Dimension Supabase (PostgreSQL 15 Engine) MongoDB Atlas (Document Cluster)
Primary Role Client Identity, Administrative Auth & ACID State Tenant User Directories & High-Throughput Telemetry
Data Models Stored clients table, admins table, bcrypt hashes. users collection, activity_logs collection.
Core Architectural Strength Relational integrity, unique constraints, strict ACID transactions. Document polymorphism, dynamic attributes, rapid append logging.
Schema Rigidity Strict relational schema enforced by PostgreSQL DDL. Schema-flexible BSON documents; supports arbitrary user metadata.
Tenant Revocation Instant: Setting is_active=false revokes all access globally. Decoupled: User records remain intact for auditing.

Why Storing Media in Databases is an Anti-Pattern

  • Storing base64 strings or binary blobs in MongoDB inflates document size and exhausts the 16MB document limit.
  • Database RAM cache (WiredTiger cache pool) becomes saturated with media data rather than index keys.
  • Offloading avatars to Firebase/GCS frees backend bandwidth and utilizes Google's global multi-region edge caches.

Google Cloud Platform (GCP) Bonus Alignment

  • Cloud Storage: Firebase Storage directly provisions Google Cloud Storage buckets.
  • Service Accounts: Authenticated via IAM Service Account credentials with least-privilege roles.
  • Cloud Run Compatibility: The backend Docker container is built to deploy natively on GCP Cloud Run.

9. Engineering Challenges & Evaluation Scorecard Section 9 & 10

9.1 Real-World Engineering Challenges & Solutions

1. Stale Session Desynchronization

Problem: When testing against ephemeral cloud database restarts, browsers retained valid JWT tokens in localStorage for tenant records that no longer existed, causing confusing 404 errors during credential generation.

Solution: Implemented an HTTP interceptor in src/services/api.js that detects 404 Client Record Not Found, immediately flushes invalid localStorage keys, and resets the UI to a clean authentication state.

2. Recursive Telemetry Polling Loops

Problem: The dashboard polls /api/v1/activity and /api/v1/insights. The logging middleware recorded these polls into MongoDB, polluting the audit table with internal self-activity.

Solution: Filtered internal telemetry routes inside logging_middleware.py and introduced domain badges in the frontend to clearly distinguish user actions from background heartbeats.

3. Super Admin Persistence across Ephemeral Container Restarts

Problem: Free cloud container instances shut down during inactivity, losing unseeded in-memory admin accounts.
Solution: Added an idempotent @app.on_event("startup") database seeder hook in main.py that automatically ensures the default Super Admin account (admin / adminpassword123) exists on boot.
