1. Project Overview & Problem Statement

This project is a complete full-stack, cloud-native user management platform built for multi-tenant software-as-a-service (SaaS) environments.

In multi-tenant cloud applications, different client organizations share computing infrastructure. The primary engineering challenge is ensuring strict tenant data isolation so that one client cannot access, modify, or view another client's user directory or activity. Additionally, user identity must be cleanly separated: everyday human users access the browser interface with standard login sessions, while external microservices and developer scripts authenticate via programmatic API credentials (Client ID and Client Secret).

To solve these challenges, the platform was developed using:

  • Frontend: React 18 Single Page Application (SPA), Vite 5, Tailwind CSS, modular component structure.
  • Backend: FastAPI (Python 3.11) with asynchronous request processing, Pydantic validation, and OpenAPI 3.1 documentation.
  • Databases: Supabase (PostgreSQL) for relational client identity and credential hashes; MongoDB Atlas for tenant user records and audit logs.
  • Cloud Storage: Firebase Storage (Google Cloud Storage) for user profile avatars.
  • AI Integration: Google Gemini AI for synthesizing operational activity logs into health insights.
  • DevOps & Cloud: Docker multi-stage containerization, Docker Compose for local development, deployed live on Vercel and Render.

3. Multi-Tenant Architecture & Data Isolation

A central requirement of the assignment is demonstrating that data belonging to one client is strictly inaccessible to any other client.

3.1 How Multi-Tenancy is Enforced

We use a Shared Database with Hard Query Partitioning. In this model, all users reside in a single MongoDB collection, but every document includes a mandatory client_id field.

The backend never trusts client-supplied query parameters or request bodies to identify the tenant. Instead:

  1. The tenant logs in and receives a signed JWT token containing their verified client_id in the payload.
  2. For every database read, update, or delete request, the backend automatically injects the tenant's client_id into the MongoDB query filter:
# Backend Query-Level Isolation Guarantee (users router):
query = {
    "_id": ObjectId(user_id),
    "client_id": request.state.tenant["client_id"],
    "is_deleted": False
}
user = await db.users.find_one(query)
if not user:
    raise HTTPException(status_code=404, detail="User not found")

3.2 Why Return HTTP 404 Instead of HTTP 403?

Security Obscurity Principle:
If Tenant B tries to look up an ID belonging to Tenant A, our API responds with HTTP 404 Not Found, not 403 Forbidden. Returning 403 would inform an attacker that the user ID exists in the system (allowing ID enumeration). Returning 404 treats the record as if it does not exist, preventing cross-tenant information leakage.

3.3 Cross-Tenant Isolation Test Evidence

During automated testing against the live production deployment, Tenant A created a user (ID: 6aaa66bb5c5583ee5013bb50). When Tenant B attempted to fetch that user ID with their own valid token:

4. Authentication & API Credential Management

The application implements a Dual-Track Authentication Mechanism, clearly separating human interactive logins from machine-to-machine API integrations.

4.1 Track 1: Interactive Browser Session (For Dashboard Users)

  • The client organization registers by providing a username and password (POST /api/v1/auth/register).
  • Credentials are checked and stored in Supabase PostgreSQL with bcrypt password hashing.
  • Upon logging in (POST /api/v1/auth/login), the user receives a Session JWT (type: "session").
  • API keys (Client ID and Secret) are not generated or exposed during signup.

4.2 Track 2: On-Demand Developer API Credentials (For External Systems)

  • Inside the dashboard, an authorized tenant clicks "Generate API Credentials" (POST /api/v1/clients/credentials).
  • The backend generates a unique client_id (e.g. cli_9e7196...) and high-entropy client_secret (e.g. sec_88f912...).
  • The backend hashes the secret with bcrypt (12 rounds) and saves only the hash in Supabase.
  • The raw client_secret is displayed to the user in a pop-up modal only once. It is never stored in plain text.

4.3 Programmatic Token Exchange Flow

External applications (scripts, third-party backends, mobile apps) authenticate by exchanging their credentials for an API JWT:

6. Firebase Storage & Google Cloud Integration

Section 4 and Section 8 of the assignment specify the integration of Firebase and Google Cloud Platform (GCP).

6.1 Firebase Cloud Storage for User Avatars

Rather than saving base64 images or binary files in MongoDB (which degrades database read performance and bloats document storage), profile avatars are stored in Firebase Storage, built natively on Google Cloud Storage (GCS).

How the Upload Works:

  1. In the frontend modal, the user picks an image file. A live client-side preview is displayed.
  2. The file is sent via multipart form-data to POST /api/v1/users/upload-avatar.
  3. The backend validates the MIME type (PNG, JPEG, WebP) and streams the file buffer directly to Firebase Storage using the firebase-admin SDK.
  4. Firebase saves the file in Google Cloud Storage and returns a public CDN URL, which is then saved in the user's MongoDB record.

6.2 Google Cloud Platform (GCP) Alignment

  • Cloud Storage: Firebase Storage directly utilizes Google Cloud Storage buckets with IAM access control.
  • Global CDN Delivery: Avatars load quickly from Google's edge cache network.
  • Serverless Cloud Run Compatibility: The backend Docker container is fully packaged and ready to run on GCP Cloud Run.

7. AI Integration: Operational Telemetry Insights

Section 1 and Section 5 ask for an AI-enabled system feature. We implemented an operational intelligence endpoint at GET /api/v1/insights.

  • Telemetry Aggregation: The backend inspects recent request records from MongoDB activity_logs, computing average latency, total request count, HTTP status breakdown, and domain actions.
  • Gemini LLM Synthesis: The system sends the performance metrics to Google Gemini AI (with a built-in mathematical heuristic fallback if the API quota is reached).
  • Outcome: Returns clear, human-readable operational summaries to the dashboard (e.g. "Tenant Acme Corp exhibits optimal operational health with an average latency of 45ms across 12 API requests. 0% error rate detected.").

8. Dockerization & Local Development Setup

The complete application is containerized using Docker and can be run locally with a single command.

8.1 Container Architecture

  • Frontend Dockerfile: Multi-stage Alpine container. Stage 1 compiles the Vite production bundle with Node 20. Stage 2 copies the static files into Nginx 1.25 Alpine, serving the SPA on port 80 with push-state routing rules.
  • Backend Dockerfile: Python 3.11 Slim container. Caches dependencies from requirements.txt, exposes port 5000, and includes a built-in container HEALTHCHECK probe hitting http://localhost:5000/health.
  • Docker Compose: A docker-compose.yml file in the repository root allows spinning up the system locally.

10. Real Engineering Challenges & Solutions

During development and testing, several real-world issues were identified and resolved:

Challenge 1: Stale Session Desynchronization

Problem: When testing against cloud containers that restarted or re-seeded test databases, the browser retained an old JWT token in localStorage. When the user clicked "Generate API Credentials", the backend returned 404 Client record not found because the old tenant record was gone.

Solution: In src/services/api.js, we added an HTTP response interceptor. If any API call returns a 404 indicating the authenticated client record no longer exists, the frontend immediately clears localStorage and prompts the user to log in or register cleanly, preventing broken states.

Challenge 2: Recursive Telemetry Polling Loops

Problem: The dashboard automatically polls /api/v1/activity and /api/v1/insights. The logging middleware originally logged every incoming HTTP request into MongoDB, causing the activity table to be flooded with internal polling calls instead of actual user CRUD operations.

Solution: In logging_middleware.py, we excluded /activity, /insights, and /clients/me from being saved into the database. In the frontend ActivityView.jsx, we added domain action badges ("User Created", "User Updated", etc.) so users see meaningful domain operations.

Challenge 3: Super Admin Persistence Across Free-Tier Container Restarts

Problem: Free cloud container instances spin down after 15 minutes of inactivity. When restarted, an unseeded admin account could be lost if not committed to PostgreSQL.

Solution: We implemented an automatic startup event in main.py (@app.on_event("startup")) that seeds the default Super Admin account (admin / adminpassword123) idempotently on container boot.
